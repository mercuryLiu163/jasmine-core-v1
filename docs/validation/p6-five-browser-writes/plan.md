# Five milestone-B browser writes — bounded acceptance plan

Base: documentation handoff `0d5c90d` (product unchanged from item-6 release). This is a new browser-coverage slice, not a deployment, native P2 conversation Gate, P4/P7 acceptance or whole P6/V1 release. The live item-6 deployment stays on its existing release and flag 0; no live credentials, database, hooks or services are changed.

Historical gap census: `historical-gap-census.json` hashes the INDEX and all 146 browser-request traces found in the P6-01 and P6-03 integration evidence roots. There are zero POST matches for all five requested routes. This is a coverage census, not a semantic re-validation of historical bundles; their original bindings remain unchanged.

Every formal run requires a clean committed candidate, `git archive` source extraction, a newly built Dashboard, actual frozen Core routes/stores over loopback HTTP, fresh isolated SQLite/objects/keys/ports, and actual Chrome DOM clicks through the Dashboard proxy. No simulated HTTP reply may count as success. Only the Interpreter provider boundary is a clearly labelled deterministic component simulation using the Core's constructor injection seam; there is no native capture or real-model extraction claim. Raw fixture sources are explicitly labelled synthetic assistant messages, not native human prompts. Review/Rule processing and all permissions/revisions/transactions/replays remain real Core code.

For all five: independently GET the changed object and command Event and read the correlated audit through a separate operator-admin key directly from Core. Require the matching browser POST method/path, status, request ID, actor, scope, audit decision, target and command. Forced page reload/readback must use the exact object. Compare original bytes/digests before deriving masked screenshots; no token, credential header or full browser profile may enter the shareable bundle.

Each route also has a real stale-basis browser submission: prepare the DOM draft, make a labelled independent competing change on its own isolated object, then click submit. Require the exact 409 code, preserved draft/key, no automatic retry, and equality of business/source/operation tables before/after refusal (exclude audit and key usage metadata). No successful object is substituted after a failed scenario. A deliberate explicit replay of each successful browser request must reuse its original body/key and return its original receipt without a second command/child/version/application. Changed body under a used key must refuse without changes. Replay is separately labelled API evidence; only the original DOM submit closes browser coverage.

Exit gate: all five positive rows, five stale-basis rows, five replays, five changed-body refusals and all object/command/audit/provenance assertions must be present and true. Missing/false/unknown required records fail the run; do not infer success from panel text or HTTP status alone. Required record counts are frozen before execution. Preserve failed attempts and negative exit-gate evidence. Stop only processes created by the run; never use global pkill or occupied-port cleanup.

Deliver `scenario.md`, `click-trace.jsonl`, masked `api-requests.jsonl` and `api-responses.jsonl`, `truth-before-after.json`, object/source/command/audit mappings, screenshots, raw build/test logs, `result.md` and hash inventory `manifest.json`. Runtime credentials and DB live in a separate private temporary directory, not the shareable inventory. A successful run is `PASS_FIVE_BROWSER_WRITES_SCOPED`; independent review/validation remains a separate required conclusion tied to this candidate. It must not be represented by the implementer's own PASS.

Implementation scope is harness/tests/documentation only. If a product defect appears, preserve the failing evidence and describe the required change; any fix needs its own final source binding and applicable revalidation. No main merge, deployment change, item-6 enablement or daily-use release is authorized by this slice.
