# ADR 0006: Task and Step state in P1

Status: accepted for P1-02 implementation. Design input: module design §6 and P1 taskbook.

## Projection and migration

`m0004_task_step_state` upgrades every P0 Task `open` to `ACTIVE`, including existing databases. Task states are `ACTIVE`, `BLOCKED`, `ACCEPTED`, `CANCELLED`; Step states are `PLANNED`, `IN_PROGRESS`, `EXECUTED`, `VERIFIED`, `ACCEPTED`, `FAILED`, `BLOCKED`, `STALE`, `SKIPPED`. New Task rows start `ACTIVE`, new Step rows start `PLANNED`. `stp_` identifies a Step. Every successful mutation appends an immutable Event before changing its projection in one `BEGIN IMMEDIATE` transaction. Any validation or commit failure leaves both unchanged. A replay of the same Event ID and semantic request returns the original Event and original response snapshot, including original revisions and Evidence IDs.

Task and Step each have independent positive revision counters. Step creation requires the current Task revision and increments it. Step transition and Step criteria update require the current Step revision and increment both Step and Task revisions. This permits independent Steps to progress concurrently; Task revision is the aggregate change marker, not a second lock on Step writes. Task transition, criteria update and acceptance require the current Task revision. Conflicts use `409 revision_conflict` and return the current snapshot. Missing or boolean/invalid expected revisions are rejected.

A terminal Task (`ACCEPTED` or `CANCELLED`) disallows child writes. An accepted Task is final in P1. A cancelled Task may return to `ACTIVE` only by a human/system actor with `state:accept`, a reason, and the current Task revision. `ACTIVE→BLOCKED`, `BLOCKED→ACTIVE`, `ACTIVE/BLOCKED→CANCELLED` require a reason. No implicit recovery occurs.

The original Step edges are `PLANNED→IN_PROGRESS`, `IN_PROGRESS→EXECUTED|FAILED|BLOCKED`, `EXECUTED→VERIFIED|FAILED|STALE`, `VERIFIED→ACCEPTED|STALE`, and `FAILED|BLOCKED|STALE→IN_PROGRESS`. The explicit P1 additions are `PLANNED|IN_PROGRESS|EXECUTED|FAILED|BLOCKED|STALE→SKIPPED` and `SKIPPED→IN_PROGRESS`. Skip and recovery require reason plus `state:accept` and human/system identity. `ACCEPTED` is final. An Agent cannot receive `state:accept` or self-accept.

## Acceptance and Evidence

Acceptance criteria have the exact structure `{"requirements":[{"key":"build","kind":"BUILD","required_result":"PASS"}]}`. `key` is unique per object. `kind` is one of `COMMAND_RESULT`, `BUILD`, `TEST`, `DEVICE_TEST`, `FILE_CHANGE`, `ARTIFACT`, `REVIEW`, `USER_CONFIRMATION`; `required_result` is `PASS` except `USER_CONFIRMATION` may also require `INFO`. Optional exact match fields are `tool_name` (nonempty text, at most 512 characters), `command_sha256`, and `artifact_sha256` (each exactly 64 lowercase hexadecimal SHA-256 characters). Unknown fields are refused. Criteria can be empty while work is being planned, but an empty Step cannot become `VERIFIED` or `ACCEPTED`, and an empty Task cannot become `ACCEPTED`. Nonempty Task/Step criteria at creation or any criteria update require `state:accept` and a human/system actor. This prevents an Agent from weakening requirements; creating an empty Task/Step is allowed but cannot bypass verification.

`EvidenceValidator.validate(EvidenceRequest)` returns `EvidenceValidationResult(evidence_ids, rule_versions)` or throws `missing_evidence`. The request includes current Task/Step snapshots, target status, criteria, actor identity, current expected revision and whether a distinct current `USER_CONFIRMATION` is required. The validator runs inside the state transaction before Event append; successful IDs and applicable Authority Rule versions are frozen in the transition Event, history and response. The default validator always refuses. P1-03 must install a real validator that checks each criterion, Raw source Event, current workspace fingerprint, and current revision; it must also enforce applicable active `ACCEPTANCE/VERIFY` Authority rules. `ACCEPTED` requires an independent current `USER_CONFIRMATION` for the exact Task/Step and revision, even if test Evidence exists. No Agent assertion or review alone establishes acceptance.

Task acceptance requires an `ACTIVE` Task, at least one `ACCEPTED` Step, all other Steps either `ACCEPTED` or explicitly `SKIPPED`, nonempty Task criteria, human/system `state:accept`, and current Evidence plus confirmation. No empty Task or all-skipped Task can pass. P1-02 rejects `VERIFIED` and `ACCEPTED` until P1-03 supplies real Evidence validation.
