# ADR 0007: P1 Evidence, workspace fingerprint and bounded Codex hooks

Status: implementation candidate. Real Codex Gate remains a separate verdict from component tests.

## Evidence and Rule version content

`m0005_evidence_fingerprint` adds append-only `evidence`, `workspace_fingerprints`, and `rule_verification_requirements` tables. `evd_` identifies Evidence. SQLite UPDATE, DELETE and INSERT-on-existing-key triggers protect all three tables, including `INSERT OR REPLACE` with `recursive_triggers=OFF`. Tool Evidence is written in one transaction: a `tool.call` Raw Event, a `tool.result` Raw Event containing the producer's tool response, an `evidence.recorded` Event, and the Evidence projection. Retries use deterministic Event IDs derived from the Codex session, turn and tool-use ID. The command/source identity is canonical JSON, so delimiters inside IDs cannot alias another call. The first projection and snapshot are returned on replay. No failure may leave only one side committed.

Generic zero-exit tool output produces `COMMAND_RESULT/PASS` only when the trusted response explicitly carries integer `exit_code` or `exitCode` equal to zero and `is_error` is not true. Nonzero/error is `FAIL`; absent exit status is `INFO`. The API permits only a Registry `system` actor with `evidence:write`, and key issuance refuses that scope for other actor kinds. A model-selected `kind` cannot promote an arbitrary command: specialized kinds require an exact `(kind, tool_name, command_sha256)` entry in an owner-only `JASMINE_CORE_EVIDENCE_PRODUCERS` JSON file outside the controlled workspace. Its SHA-256 is frozen in Evidence and rechecked during validation. This is a trusted producer classification, not proof that the test design was good. The current Codex PostToolUse adapter sends generic `COMMAND_RESULT` only. T10 pins both `tool_name` and `command_sha256` in criteria; it does not claim real TEST or DEVICE_TEST coverage.

An Authority proposal or same-scope supersede may include exact `verification_requirements` with the ADR 0006 requirement shape. The mapping is inserted with that immutable Rule version and its command Event, and the command's idempotency digest includes it. There is no attach or edit endpoint for an ACTIVE version. Approval by a human/system with `authority:manage` activates the proposal; an Agent proposal and its origin Event remain separately attributed. An older active `ACCEPTANCE`/`VERIFY` Rule without a mapping fails State validation with `missing_evidence` until an authorized new version supplies one. The validator enumerates every applicable ACTIVE global/project/task Rule inside the State write transaction, matches each requirement, and stores exact `(rule_id,version)` references and Evidence IDs in the transition Event. An Evidence item predating the current Rule activation cannot satisfy that version. A USER_CONFIRMATION requirement names its current Rule/version; it cannot waive TEST or DEVICE_TEST conditions. HARD DENY remains a Guard policy, not an Evidence waiver.

Step Evidence belongs to the latest Step `IN_PROGRESS`/criteria cycle. Task acceptance can consume Evidence from each Step's latest cycle; task-scoped Evidence must follow Task criteria changes and later Step restarts. A Step tool result captured at its IN_PROGRESS revision remains usable after the normal EXECUTED revision increment. A retry after FAILED/STALE begins a new cycle and invalidates the old PASS. Step and Task revision counters are compared independently. `ACCEPTED` also needs an independent current human `USER_CONFIRMATION`, bound to the exact Step or Task revision and fingerprint. A Registry human with `evidence:confirm` sends the structured confirmation command, citing a real same-task human `user.prompt` Event after the current relevant State Event. The prompt Event and confirmation Event remain distinct; old prompt text cannot be reused at a later revision. No natural-language keyword extraction is claimed.

`artifact_uri` is `workspace:/relative/path`; its SHA-256 is read with descriptor-relative `O_NOFOLLOW` opens. Reads and validation check that reference again; missing or changed content is `BROKEN_REFERENCE` and cannot satisfy a requirement. Evidence source Event actor/task/project and actual result-derived status are checked before use. GETs remain read-only. A trusted `POST /v1/workspaces/fingerprint` refresh scans the current workspace and, in the same Event-first transaction, moves any now-invalid VERIFIED Step to STALE with a `step.staled` Raw Event and revision increments. The validation transaction itself raises `missing_evidence` without trying to persist STALE inside a rollback.

## Fingerprint scope

The operator sets `JASMINE_CORE_WORKSPACE_ROOT` to one controlled workspace. Git mode hashes tracked and nonignored untracked regular files plus the exact project `.codex/hooks.json` binding even if ignored. Plain-directory mode hashes **only** operator-declared paths; with no declaration it is partial/UNKNOWN rather than scanning arbitrary credentials. Root `.git`, `.codex` private state other than `hooks.json`, `.jasmine`, `evidence`, `artifacts`, and `_archive` are excluded from Git discovery; nested source directories with those names are included. Runtime DB/token names and SQLite sidecars are excluded only at the workspace root; a tracked `src/auth.json` or `src/fixture.db` remains relevant. Explicit ignored or plain-directory inputs are added as workspace-relative paths through `JASMINE_CORE_FINGERPRINT_EXTRA_PATHS` (JSON array); artifact content is independently checked even when ignored. Unlisted ignored/generated inputs are outside the declared P1 coverage and must be listed when relevant to a criterion. Snapshot records algorithm `jasmine-workspace-sha256-v1`, coverage, extra paths, Git HEAD, and the full selected-path hash map. Equal HEAD alone does not mean equal workspace. Unknown/partial scans, changed coverage, symlink/nonregular paths, unavailable Git metadata, and file/byte caps cannot compare SAME. Descriptor opens are nonblocking, so a declared FIFO is rejected without waiting for a writer. No scan follows a symlink outside root or reads `_archive` or unrelated projects.

## Hook boundary and Gate

`scripts/p1-codex-hook-install.py` adds project-local P1 UserPromptSubmit, PreToolUse and PostToolUse entries, preserving the existing P0 UserPromptSubmit entry byte-for-byte within its JSON object. It backs up a changed hooks file, is idempotent, supports `--dry-run`, and never edits global hooks, `config.toml`, or trust. The P1 adapter reads owner-only binding/token files from an owner-only runtime directory. No token is in hook JSON or argv. The operator launches a specific Codex process with a private `JASMINE_CORE_GATE_NONCE`; its first genuine P1 UserPromptSubmit atomically claims the actual session ID in an owner-only lease. A different/no nonce is unbound and receives advisory `{}`. Matching nonce with missing, corrupt, or mismatched lease makes bound PreToolUse return the official native `hookSpecificOutput.permissionDecision="deny"` shape. The first and later bound prompts are written as task-scoped `codex-p1-bound` Raw Events with the human token; P0 capture remains unchanged and separate.

The P1 bound prompt uses a system read token to fetch only its bound Task, Step, and ACTIVE Rules, and returns a compact official UserPromptSubmit `additionalContext` object. It blocks that prompt if state/rules cannot be read or the full Rule set exceeds the supported 20-Rule/8-KB context cap; HARD rules are never silently truncated. This is a minimal P1 read path, not a P3 Context Pack. The installer matches only canonical Codex `Bash` tool calls for Pre/Post. The adapter resolves a deliberately narrow set of simple Bash actions (`pwd`, `true`, `touch`, `rm`, `cat`, `ls`); compound commands, unsupported actions, noncanonical paths, symlink components and missing path context are denied when bound. Guard `DENY` and `CONFIRM` become native deny; `VERIFY` permits the tool to run but the State validator retains its Evidence requirement. Pre failures deny. PostToolUse records factual results and refreshes the fingerprint after execution; it cannot undo side effects. The safe trace records session/turn/tool-use IDs, outcome, Event ID and an input hash, never raw command arguments, response, prompt or tokens. A trace failure emits a nonsecret stderr diagnostic and cannot become a PASS claim.

Only the exact Bash action and path exercised by the real Gate may be called ENFORCED after Codex invokes the trusted hook and the target tool is observed not to run. Other local or hosted tool paths, unsupported Bash forms, and hook trust outside this session remain unverified. Synthetic hook calls and component acceptance cases establish code behavior, never the real T10 verdict. A missing trust prompt, absent entry, missing real session, or unsupported hook path is recorded as BLOCKED, not a fabricated PASS. A run that executes a forbidden tool or violates the assertions is FAIL. The Gate uses an isolated nonsensitive fixture repository and private scratch Core. Its runner stops the scratch Core; the coordinator restores or removes temporary hook entries after review. Neither path reconnects retired V0 components.
